mobie architecture01

The driver creates the offered ride in the staging app. The caller searches and requests a ride through the phone assistant. The backend stores the request, and the driver approves it in the app. The custom street-name matcher is an optional challenge extension and our proposed improvement.

The driver publishes first. A submitted passenger request remains pending until the driver approves it.

mobie architecture02

The two lanes describe the user processes, with sequence flowing down each lane. The driver must create the offered ride before the passenger can find it. The passenger calls the assistant, resolves the desired locations, selects a returned ride and explicitly agrees to submission. mobie stores a pending request. The driver reviews and approves it in the staging app, and the passenger verifies the approved booking in the app. No automatic phone notification after approval is assumed.

Test prerequisites: separate staging passenger and driver accounts, driver approval and a vehicle, a future test ride, and the starter authorized as the same passenger. If the passenger refuses or consent is unclear, the assistant does not submit a request. The approval path shown here is the successful test scenario.

mobie architecture04

A phone app session does not transfer credentials to the local starter. For the challenge, one signed-in staging passenger represents all callers to a starter instance. Restarting the starter clears its tokens and requires a fresh login. The starter uses public Auth0 client configuration with PKCE and needs no client secret. Separate instances or a new identity design are required for multiple passenger identities.

mobie architecture05

The repository is editable application code running as a server on the laptop. src/auth/ handles login and refresh. src/inbound/ exposes routes. src/mapbox/ maps location candidates. src/mobie/ validates payloads and calls staging. The starter has no per-call store or phone-provider integration. The confirmation boolean is a guard, not proof that the caller spoke consent.

Where difficult names go wrong

Speech recognition, location lookup and ambiguity need different remedies

01

Speech recognition

The spoken name becomes an incorrect transcript.

Possible remedy

Provider vocabulary hints where supported, repetition or spelling.

02

Location lookup

The transcript contains an imperfect spelling or missing context.

Possible remedy

Match against real address candidates using municipality and postcode.

03

Ambiguity

Several valid places share the same street name.

Possible remedy

Ask a question that distinguishes the candidates, then read back the choice.

Challenge example

“Gartenstraße” exists in both 6832 Sulz and 6833 Klaus. The assistant must retain which place is the start and which is the destination.

The evaluation brief includes a ride from Gartenstraße in Sulz to Gartenstraße in Klaus. We have not yet observed a baseline phone transcript proving which stage causes errors. Obtain real test calls before attributing failure to a provider. Mapbox receives written queries, not audio.

Proposed extension: implement candidate matching in the starter location service. Two credentials

Assistant to starter uses STARTER_API_KEY.

Starter to mobie uses the passenger’s Auth0 access token.

Payload rules

Numeric longitude and latitude. Time includes Z or a Vienna offset for the travel date.

Keep passenger trip data and the selected ride.id.

mobie architecture09

Use Authorization: Bearer <STARTER_API_KEY> for the starter and Content-Type: application/json for POSTs. GET /api/me verifies the account. GET /api/rides/{rideId}/rider-detail requires driver approval. GET /api/rides/{rideId} is driver-only. Search returns a raw array and [] means no matches. Seats are limited to 1–8 by the starter. Relative dates must be resolved in Europe/Vienna with the date-appropriate offset. Estimates documented as cents must be converted before speaking euros. Null is not a free price.

mobie architecture11

The starter checks confirmed === true and strips that field before forwarding to mobie. The flag does not prove spoken consent. The backend stores a real request and pending booking, subject to driver approval. Do not blindly retry booking writes after a timeout because a write may already have succeeded. The starter performs no automatic write retry. A staffed operator handoff is a separate scope decision and is not implemented.
